BITACORA DE CAMBIOS REALIZADOS DESDE EL INICIO HASTA AHORA

Proyecto:
App-GestionRecursosCLCD-

Objetivo general del trabajo realizado:
Preparar la aplicacion para poder ejecutarse primero en ambiente local con Docker y, una vez validada, dejar la base lista para moverla despues al servidor.

==================================================
1. REVISION INICIAL DEL PROYECTO
==================================================

Al inicio se hizo una lectura general del repositorio para entender su estructura y funcionamiento.

Se identifico lo siguiente:
- El proyecto es un monorepo sencillo.
- El backend esta en Node.js con Express y PostgreSQL.
- El frontend esta en React con react-router-dom y styled-components.
- El backend arranca desde `backend/index.js`.
- La conexion a base de datos depende de variables de entorno leidas en `backend/config.js`.
- El frontend consume la API con muchos `fetch(...)` directos desde componentes.
- La URL del backend estaba escrita de forma fija con la IP:
  `http://148.206.162.62:4000`
- El flujo mas delicado del sistema es el de prestamos, porque afecta stock de materiales y usa transacciones.

Tambien se detectaron riesgos importantes:
- Las contrasenas se comparan en texto plano en login.
- No hay autenticacion robusta del lado servidor.
- Gran parte del control de acceso depende de `localStorage`.
- La URL del backend estaba acoplada a una sola IP, lo que complicaba el paso a Docker.

==================================================
2. OBJETIVO DE LA DOCKERIZACION
==================================================

Se definio una estrategia por etapas:

Etapa 1:

Etapa 2:

Etapa 3:
Con el ambiente local estable, preparar el despliegue en servidor.

3. CAMBIOS HECHOS EN EL BACKEND
==================================================

Archivo modificado:
- `backend/index.js`

Cambio realizado:
- Antes el backend escuchaba siempre en el puerto fijo 4000.
- Se modifico para que lea el puerto desde variable de entorno:
  `const PORT = process.env.PORT || 4000;`

Beneficio:
- Esto permite que el backend funcione correctamente dentro de Docker y tambien en otros ambientes sin tener que editar el codigo.

Estado final:
- El servidor ahora arranca con `app.listen(PORT)`.
- El mensaje de consola se actualizo a:
  `Server on port ${PORT}`

5. ARCHIVOS NUEVOS PARA DOCKERIZACION
==================================================

Se agregaron varios archivos nuevos para contenerizar la aplicacion.

--------------------------------------------------
5.1 Dockerfile del backend
--------------------------------------------------

Archivo nuevo:
- `backend/Dockerfile`

Funcion:
- Construir una imagen de Node para ejecutar el backend.

Comportamiento:
- Usa `node:20-alpine`
- Crea `/app` como directorio de trabajo
- Copia `package.json` y `package-lock.json`
- Instala dependencias con `npm ci --omit=dev`
- Copia la carpeta `backend`
- Expone el puerto `4000`
- Ejecuta `node backend/index.js`

Beneficio:
- El backend ya puede ser levantado como contenedor independiente.

--------------------------------------------------
5.2 Dockerfile del frontend
--------------------------------------------------

Archivo nuevo:
- `frontend/Dockerfile`

Funcion:
- Construir el frontend en una etapa de build y servir el resultado con Nginx.

Comportamiento:
- Primera etapa:
  - Usa `node:20-alpine`
  - Instala dependencias del frontend
  - Ejecuta `npm run build`
- Segunda etapa:
  - Usa `nginx:1.27-alpine`
  - Copia la configuracion de Nginx
  - Copia el build generado a `/usr/share/nginx/html`
  - Expone el puerto `80`

Beneficio:
- El frontend deja de depender del servidor de desarrollo de React en produccion.
- Se sirve como build estatico, que es lo correcto para Docker y servidor.

--------------------------------------------------
5.3 Configuracion de Nginx para frontend y proxy API
--------------------------------------------------

Archivo nuevo:
- `frontend/nginx.conf`

Funcion:
- Servir el frontend React.
- Redirigir las peticiones `/api/` hacia el backend.

Comportamiento:
- `location /api/` hace proxy a:
  `http://backend:4000/`
- `location /` usa:
  `try_files $uri $uri/ /index.html;`

Beneficio:
- Permite que React funcione como SPA.
- Permite que las llamadas a `/api` lleguen al backend sin exponer internamente nombres raros al usuario.
- Es la pieza que hace posible usar rutas relativas en frontend.

--------------------------------------------------
5.4 docker-compose.yml
--------------------------------------------------

Archivo nuevo:
- `docker-compose.yml`

Funcion:
- Orquestar los contenedores del proyecto.

Servicios definidos:

1. `db`
- Imagen: `postgres:16-alpine`
- Variables:
  - `POSTGRES_DB`
  - `POSTGRES_USER`
  - `POSTGRES_PASSWORD`
- Mapea puerto externo configurable hacia `5432`
- Usa volumen persistente:
  `postgres_data`
- Monta:
  `./docker/postgres/init:/docker-entrypoint-initdb.d:ro`

2. `backend`
- Se construye desde `backend/Dockerfile`
- Variables:
  - `PORT=4000`
  - `DB_HOST=db`
  - `DB_PORT=5432`
  - `DB_USER`
  - `DB_PASSWORD`
  - `DB_DATABASE`
- Expone el puerto configurable del backend

3. `frontend`
- Se construye desde `frontend/Dockerfile`
- Depende del backend
- Expone el puerto configurable del frontend

Beneficio:
- Ya existe una forma unica y repetible de levantar toda la aplicacion.

Nota importante:
- Actualmente `docker-compose.yml` muestra el puerto externo de Postgres como:
  `${POSTGRES_PORT:-5436}:5432`
  Esto significa que localmente se puede exponer en 5436 si se desea evitar conflicto con una instalacion local existente de PostgreSQL.

7. AJUSTES DE FLUJO Y RECOMENDACIONES DE USO LOCAL
==================================================

Tambien se dejo definida la forma recomendada de trabajar primero en local:

Pasos recomendados:
1. Crear `.env` a partir de `.env.example`
2. Colocar el SQL dentro de `docker/postgres/init/`
3. Ejecutar:
   `docker compose down -v`
4. Ejecutar:
   `docker compose up --build`

Motivo del `down -v`:
- Postgres solo ejecuta los scripts de inicializacion la primera vez que se crea el volumen.
- Si el volumen ya existia, el SQL no se vuelve a correr.

Objetivo de esta estrategia:
- Verificar que todo funcione en local antes de moverlo al servidor.
